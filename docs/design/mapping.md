# Дизайн: поняття Construct → Godot

> Статус: **чернетка v0.1**. Етап 1 дорожньої карти (`docs/ROADMAP.md`).
> Це **єдине місце**, де вирішується, чим кожне поняття Construct є в Godot. Інші документи
> посилаються сюди, а не повторюють таблиці.

## 0. Простими словами

Користувач думає поняттями Construct: рівень, шар, тип об'єкта, змінна інстансу, behavior.
Під капотом це звичайні речі Godot: сцени, ноди, групи, скрипти. Документ фіксує, що чому
відповідає і **що від користувача ховаємо**. Головне правило: проєкт лишається звичайним
проєктом Godot. Його можна відкрити в чистому Godot, а програміст може дописати GDScript поруч
з аркушами.

## 1. Що ховаємо, а що показуємо

| Поняття Godot | Користувач бачить | Як |
|---|---|---|
| Сцена | **Рівень** або **Тип об'єкта** | залежно від ролі сцени (§3, §6) |
| Нода | **Об'єкт** (інстанс) | дерево нод — лише в режимі «Експерт» |

## 3. Типи об'єктів

### 3.1 Два різновиди типу

| Різновид | Що це в Godot | Можна створити дією? | Приклад |
|---|---|---|---|
| **Тип-сцена** | Окрема сцена `.tscn`; на рівні — її інстанси | так | Enemy, Coin, Bullet |
| **Об'єкт рівня** | Нода прямо в сцені рівня, без окремої сцени | ні (він один і вже є) | HUD-напис, двері рівня, головна камера |

У Construct такої різниці немає: кожен об'єкт є типом. У Godot окрема сцена для кожного напису
в HUD — це зайва морока, тому об'єкт рівня — легкий варіант. Його можна будь-коли перетворити
на тип-сцену кнопкою «Зробити типом» (це «Save Branch as Scene» у Godot).

Обидва різновиди отримують групу з назвою типу, тому для picking і аркуша вони однакові.

### 3.2 Назва типу і група

- Назва типу: `PascalCase`, унікальна в проєкті. За замовчуванням — з імені файлу сцени
  (`big_enemy.tscn` → `BigEnemy`).
- Група Godot має **ту саму назву**, що й тип (`&"Enemy"`), тож згенерований код лишається
  читабельним. Редактор не дає створити власну групу з назвою існуючого типу чи сімейства.
- Група записується в `.tscn` (persistent group), тож працює і без нашого редактора.
- Перелік типів проєкту будується скануванням сцен. Кеш лежить у `.godot/`, а не у файлі проєкту.

### 3.3 «Вид об'єкта» = клас кореня

У Construct фізика чи платформер — це behaviors. У Godot від цього залежить **клас кореневої
ноди**: `CharacterBody2D` рухається кодом, `RigidBody2D` — фізикою, `StaticBody2D` — стіна.
Тому при створенні типу користувач обирає **вид**:

| Вид (для користувача) | 2D | 3D |
|---|---|---|
| Картинка / Модель (без фізики) | `Sprite2D` / `AnimatedSprite2D` | `Node3D` + модель |
| Персонаж | `CharacterBody2D` | `CharacterBody3D` |
| Фізичний об'єкт | `RigidBody2D` | `RigidBody3D` |
| Стіна / Платформа | `StaticBody2D` | `StaticBody3D` |
| Зона (тригер) | `Area2D` | `Area3D` |
| Текст | `Label` | `Label3D` |
| Елемент інтерфейсу | `Button`, `LineEdit`, `HSlider`… | (через 2D-інтерфейс поверх 3D) |

- Behavior може вимагати вид: Platformer потребує «Персонаж». Якщо додати Platformer до
  «Картинки», редактор запропонує змінити вид («Change Type» у Godot) і сам перенесе спрайт
  дочірньою нодою.
- **Форма зіткнень створюється автоматично:** для виду з фізикою — прямокутник/капсула за
  розміром спрайта (2D) або опукла форма за мешем (3D). Користувач може її підправити, але
  не мусить. У Construct форма береться зі спрайта сама, і новачки не знають, що в Godot це окрема нода.

### 3.4 Змінні інстансу

- Зберігаються як `@export`-змінні **скрипта типу**: невеликого файлу поруч зі сценою
  (`enemy.gd`), який веде панель «Змінні». Файл має заголовок «керується редактором змінних».
- Так змінні видно в інспекторі Godot з типами й межами, і їх можна перевизначити для окремого
  інстансу на рівні. Звичайний GDScript теж може їх читати (`enemy.health`).
- Якщо в кореня **вже є скрипт програміста**, його `@export`-змінні стають змінними інстансу
  автоматично (`ace-format.md` §5.3), а панель «Змінні» показує їх лише для читання з кнопкою
  «Редагувати в коді».
- Типи змінних — з `expressions.md` §2: число (`float`), текст, так/ні, список, словник.

### 3.5 Behaviors

- Behavior — це **дочірня нода** в сцені типу (`Platformer`, `Sine`…). Тож усі інстанси типу
  отримують його автоматично, як у Construct.
- Налаштування behavior для окремого інстансу (наприклад, швидкість лише цього ворога)
  у Godot вимагає «Editable Children». Наш інспектор показує властивості behaviors прямо
  на інстансі й сам вмикає це, коли щось змінено.
- Behavior шукає свого «господаря» як батьківську ноду. ACE behavior звертаються до нього через
  `{behavior}` (`ace-format.md` §3).
- Кілька behaviors одного класу на типі — дозволено з різними іменами (як у Construct).

### 3.6 Ефекти

- 2D: згенерований `ShaderMaterial` у `material` об'єкта.
- 3D: `material_overlay` або генерація матеріалу поверх існуючого (визначити на етапі 5).
- Ефект шару (2D): повноекранний прямокутник з шейдером на `CanvasLayer` (через `BackBufferCopy`).
- Пост-обробка 3D: `Environment` (glow, туман, кольорокорекція), а також `Compositor` для складних ефектів.

### 3.7 Сімейства

- Сімейство = група Godot, яку редактор додає кореням усіх типів-членів.
- ACE сімейства — спільні для всіх членів (`ace-format.md` §2.2).
- Змінні сімейства (у Construct «family instance variables») — пізніше; поки змінні лише на типах.

## 4. Об'єкти-плагіни Construct → Godot

У Construct навіть клавіатуру треба «додати в проєкт». У нас ввід, звук, сховище й час
**доступні завжди** як системні категорії ACE, нічого додавати не треба.

| Construct | 2D | 3D | Примітка |
|---|---|---|---|
| Sprite | `Sprite2D` / `AnimatedSprite2D` | модель `.glb` (`Node3D` + `AnimationPlayer`) | |
| Text / Sprite font | `Label` | `Label3D` | |
| Tiled Background | `Sprite2D` (region + repeat) / `TextureRect` (tile) | — | |
| 9-patch | `NinePatchRect` | — | |
| Tilemap | `TileMapLayer` | `GridMap` | |
| Particles | `CPUParticles2D` / `GPUParticles2D` | `GPUParticles3D` | |
| Button, Text input, List, Slider | `Button`, `LineEdit`, `ItemList`/`OptionButton`, `HSlider` | ті самі поверх 3D | |
| Audio | системна категорія «Звук» (пул `AudioStreamPlayer`) | `AudioStreamPlayer3D` для позиційного | |
| Keyboard, Mouse, Touch, Gamepad | системна категорія «Ввід» (`Input`) | те саме + промінь з камери для миші | |
| Array, Dictionary | змінні типу «список» і «словник» | | `expressions.md` §2 |
| JSON | системна категорія «Дані» | | |
| Local Storage | системна категорія «Збереження» (`user://`) | | |
| AJAX | системна категорія «Мережа» (`HTTPRequest`) | | |
| Browser | системна категорія «Платформа» (`OS`, `JavaScriptBridge`) | | |
| 3D Shape (C3) | — | `CSGBox3D`, `CSGSphere3D`… | у нас 3D повноцінне |

## 5. Одиниці й координати

| Що | Користувач бачить | У Godot | Компілятор |
|---|---|---|---|
| Позиція 2D | пікселі, (0,0) зліва вгорі, Y вниз | те саме | без змін |
| Позиція 3D | метри, Y вгору | те саме | без змін |
| **Кути** | **градуси** (2D — за годинниковою стрілкою, як у Construct) | радіани | `deg_to_rad` / `rad_to_deg` у шаблонах ACE |
| Обертання 3D | градуси по осях X/Y/Z | `rotation_degrees` | |
| **Прозорість** | **0–100** (як у Construct) | `modulate.a` 0–1 | ділення на 100 у шаблоні ACE |
| Колір | `rgb(0–255, …)` | `Color` 0–1 | `expressions.md` §5 |
| Час | секунди | секунди | |
| Швидкість | пікселів/с (2D), метрів/с (3D) | те саме | |

Правило: **жодних радіан і жодного 0–1 у полях, які бачить користувач.** Перетворення
роблять шаблони ACE, а не користувач.

## 6. Рівні, шари, камери

### 6.1 Рівень
- Рівень = сцена з кореневою нодою `Node2D` (2D) або `Node3D` (3D) і нодою-раннером аркуша.
- Розмір рівня (у Construct «layout size») — властивість раннера. Використовується для меж
  камери й behavior «Знищити за межами».
- «Перейти на рівень» → `change_scene_to_packed()`. «Перезапустити рівень» → `reload_current_scene()`.

### 6.2 Шари (2D)
- Шар = `CanvasLayer` з `follow_viewport_enabled = true` (рухається з камерою).
- Прапорець «Нерухомий на екрані» вимикає `follow_viewport` і дає HUD.
- Паралакс шару — `follow_viewport_scale` (найпростіше), а для складнішого — `Parallax2D`.
- Порядок шарів — `layer`. Порядок об'єктів у шарі — порядок у дереві + `z_index`;
  дії «На передній план»/«На задній план» → `move_to_front()` тощо.
- У 3D шарів немає. HUD поверх 3D — шар-`CanvasLayer` з 2D-інтерфейсом.

### 6.3 Камера
- 2D: `Camera2D`. «Прокрутити до об'єкта» / behavior «Слідувати камерою» / межі = розмір рівня.
- 3D: `Camera3D` + behaviors «Орбітальна камера», «Камера за персонажем», «Від першої особи».
- Якщо в рівні немає камери, 2D-рівень працює як у Construct (вигляд від (0,0)), а 3D-рівень
  отримує камеру автоматично, з попередженням.

### 6.4 Глобальне
- **Глобальний раннер** (autoload, створюється автоматично): тримає глобальні змінні й виконує
  **глобальний аркуш** (події, що працюють на всіх рівнях, наприклад пауза чи музика).
- **Глобальні об'єкти** — інстанси під autoload «Globals». Вони не знищуються при переході
  між рівнями.
- Порядок у кадрі: спершу глобальний аркуш, потім аркуш рівня.

## 7. 3D, якого немає в Construct

Тут орієнтуватися на Construct не вийде. Принцип той самий: прості назви, градуси, метри.

| Поняття | Godot | Для користувача |
|---|---|---|
| Модель | імпортований `.glb`/`.gltf` → сцена | тип-сцена виду «Модель» або «Персонаж» |
| Матеріал | `StandardMaterial3D` | «Колір», «Текстура», «Блиск» в інспекторі |
| Світло | `DirectionalLight3D`, `OmniLight3D`, `SpotLight3D` | «Сонце», «Лампа», «Прожектор» |
| Небо й атмосфера | `WorldEnvironment` | «Небо», «Туман», «Яскравість» |
| Навігація | `NavigationRegion3D` + `NavigationAgent3D` | behavior «Шукати шлях»; сітка навігації будується кнопкою |
| Рівень з блоків | `CSG*`, `GridMap` | конструктор рівнів (етап 4) |
| Промінь | `RayCast3D` / запит до `PhysicsDirectSpaceState3D` | умова «Бачить…», вираз «Відстань до перешкоди» |

## 8. Поки не відображаємо

| Construct | Чому поки ні | Що робити зараз |
|---|---|---|
| Containers | рідко потрібні новачкам; складна семантика picking | дочірні ноди в сцені типу |
| Persist | залежить від системи збережень | після «Save/Load» |
| Сталий UID між запусками | `get_instance_id()` змінюється | якщо знадобиться, persistent id в метаданих |
| Змінні сімейств | потребує спільного скрипта для різних класів | змінні на кожному типі |
| Мультиплеєр | великий окремий етап | після 1.0 |

## 9. Відкриті питання

1. Скрипт типу (§3.4) — це файл, що генерується, але комітиться. Чи прийнятно, чи краще
   метадані (`set_meta`), без файлу, але повільніше і без типів в інспекторі? Пропоную скрипт.
2. «Editable Children» для налаштувань behavior окремого інстансу (§3.5) — перевірити, що
   Godot не зберігає в рівень зайвого.
3. Ефекти в 3D (§3.6) — overlay чи генерація повного матеріалу.
4. Об'єкти рівня (§3.1): чи дозволяти «Створити» для них клонуванням ноди? Пропоную ні,
   щоб правило було просте.
5. Поле `requires` (вид об'єкта для behavior, §3.3) — описати в окремому документі про behaviors.
